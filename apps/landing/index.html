The problem

Two things every site wants, and today they fight.

To know you are a student, a site has to see your student address — which it then keeps, mails, and leaks when it is breached. And to stop one person taking the free tier fifty times, it has to recognise the person.

A unique-email column does not do the second. ana+1@gmail.com, ana+2@gmail.com and a.n.a@gmail.com are one inbox and three rows. Fifteen characters of local part give sixteen thousand spellings of the same mailbox, all of which deliver.

What a site holds today

  • Your full address, forever
  • Your name, usually
  • A row in the next breach dump
  • No way to tell you from your other four accounts

What it holds with MailProof

  • That the domain is educational
  • That this is the first claim from that mailbox
  • An opaque handle it cannot reverse
  • Nothing else

How it works

Three steps, and the third one is the interesting one.

Nothing here asks you to trust us about your inbox. The proof is the sending domain's own signature, which every mail provider already attaches to everything it sends.

01

The site shows a code

Something like MP-4KQ7-9XW2-3TFA. It expires in minutes and only authenticates for that one site.

02

You send yourself an email

From the address you want to prove, with the code in it. One click with the extension, or a file upload in any browser.

03

The claim is spent, once

Your mailbox becomes an unguessable value on Midnight. The site sees the domain and a first-time flag — never the address.

The detail that matters

Why you send the email, instead of us sending it.

The obvious design is to email you and have you click a link. That proves nothing useful here, because the site already knew the address it wrote to.

The next idea — take an email somebody sent to you and read the recipient — is worse. Whoever sent that message chose the recipient, and the signature covers what they chose. Anyone able to sign for a domain could invent any address inside it and burn a colleague's slot before they ever arrived.

A message you sent is different. A provider will not sign a message claiming to come from a mailbox the sender does not control. That is what DKIM alignment is for, and it is the whole basis of this.

The SDK

Two calls in your own backend.

An SDK is a small library you install into your own code so you do not have to build a thing yourself. This one runs on your server, mints the codes, reads the message, applies your rules, and hands back a decision.

It never decides what to grant. That is yours. 

const mailproof = createMailProof({
  audience: 'your-site',
  challengeSecret: env.MAILPROOF_CHALLENGE_SECRET,
  blindingKey:     env.MAILPROOF_BLINDING_KEY,
  campaign: '2026-S1',

  tiers: [
    { id: 'STUDENT',   suffixes: ['.edu', '.edu.ar', '.ac.uk'] },
    { id: 'CORPORATE', notFreeProvider: true },
  ],
  domainKeys: [{ domain: 'udesa.edu.ar', dnsRecord: 'v=DKIM1; k=rsa; p=…' }],
  redemption: httpRedemptionClient({ baseUrl: 'http://127.0.0.1:3000' }),
})

const result = await mailproof.verify(eml)

if (result.ok && result.tier === 'STUDENT' && !result.alreadyClaimed) {
  await db.user.update({ where: { id }, data: { plan: 'PRO' } })
}

alreadyClaimed is a field, not an error — it is the question you were actually asking. And a domain that matches no rule gets no tier, never a default one.

Use cases

One mechanism, because the domain does the talking.

A proof always says the same thing — "controls a mailbox at D". What it is worth depends entirely on how hard a mailbox at D is to get.

Student pricing

A discount that cannot be shared

A .edu.ar is issued only to recognised institutions, so the registrar did the vetting. One benefit per mailbox stops the code circulating.

Work email required

A B2B trial without the inbox

Confirm the person works somewhere real without collecting a corporate address that becomes a sales list.

Free tier abuse

One free account per person

The thing a unique-email column has never been able to enforce, enforced — without holding the person.

Communities

A room only insiders can enter

Everyone in it is verifiably from the same institution, and nobody in it knows who anybody else is.

What we will not pretend

The limits, up front.

A privacy tool that hides its own trust assumptions is not a privacy tool. Every successful verification returns a trust object saying who read what.

Read this before you rely on it

  • Something reads the email. Today that is the attestor, which checks the message's own RSA signature. It is not you and it is not the chain — but it is not nobody.
  • The attestor is trusted. If it signs a false claim, the contract accepts it. Run your own.
  • "Not a free provider" is a friction tax, not an anti-sybil control. A one-dollar domain with catch-all mail defeats it. Gate anything that matters on an explicit list.
  • Alumni addresses outlive graduation. Campaigns are per period so a benefit has to be re-proven, but the mailbox itself may never expire.

Everything is open. Run all of it yourself.

The contract, the attestor, the daemon, the SDK and the extension are in one repository, with the decisions and the known limitations written down beside them.
